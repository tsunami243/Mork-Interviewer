# 示例样本
# 今天吃什么智能饮食推荐 Agent

## 项目简介

这是一个基于 FastAPI 和大语言模型构建的智能饮食推荐 Agent。项目目标是在用户给出预算、口味偏好、忌口食材和用餐场景后，生成真实、可执行且符合限制条件的菜品推荐。

## 核心技术实现

### 1. 四阶段推荐管线

项目将一次推荐请求拆分为四个阶段：

1. 意图提取：从用户自然语言中提取预算、口味、忌口、菜系和用餐人数等结构化条件。
2. RAG 检索：通过向量检索召回候选菜品，并结合 SQL 元数据过滤不符合预算、菜系或忌口要求的记录。
3. 规则校验：对模型输出执行菜品存在性、预算范围和属性匹配校验，过滤可能出现的幻觉内容。
4. 输出组装：将通过校验的菜品、推荐理由和注意事项组织为最终回复。

### 2. RAG 与元数据过滤

项目使用 pgvector 存储菜品知识库的向量数据。用户输入会先进行向量召回，再通过 SQL JOIN 查询菜品价格、菜系、食材标签等元数据。

例如，当用户要求“预算 30 元、想吃辣、不吃香菜”时，系统会优先召回语义相关的菜品，再过滤价格超过预算或包含香菜的候选项。

### 3. 防幻觉机制

为了避免大模型编造不存在的菜品，项目设计了三层防御：

- Prompt 层：要求模型只能基于候选菜品生成推荐，不允许编造菜名。
- 规则层：校验模型输出的菜品是否真实存在于知识库中，检查预算和属性是否匹配。
- 数据层：当模型调用失败或检索结果为空时，使用真实菜品数据作为兜底推荐。

### 4. 会话与用户画像

项目使用 Redis SessionStore 保存多轮对话历史，并通过 `session_id` 隔离不同用户的会话数据。Session 设置 TTL，过期后自动清理。

用户画像使用结构化字段保存，例如口味偏好、忌口食材、常用预算范围、菜系偏好和历史点餐记录。推荐时会综合用户当前输入和历史偏好生成个性化结果。

### 5. 工程化与可观测性

项目使用 Docker Compose 支持一键部署，并加入结构化日志和 Prometheus 指标。

接口层对 `/chat` 接口实施令牌桶限流，避免高频请求影响模型服务。项目还包含自动化测试，用于验证推荐结果是否满足预算、忌口和菜品真实性等约束。
